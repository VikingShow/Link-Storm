# Link Storm MVP 与低成本策略 v0.1

日期：2026-06-09

## 1. 当前阶段目标

先做一个能跑通核心闭环的基础版本：

```text
用户选择城市和兴趣
-> 系统读取可信内容和活动
-> 整合成事件级情报
-> 用低成本推荐算法排序
-> 推荐相关本地活动
-> 用户收藏、反馈、加入日程
```

第一版不追求全自动、全智能，而是验证产品体验和推荐逻辑。

## 2. 额外亮点建议

这些是后续可以增强产品差异化的功能，第一阶段只预留数据结构，不急着实现。

### 2.1 机会链路

把一条情报和用户能做的事情串起来：

```text
行业信号
-> 相关公司
-> 附近活动
-> 可学习资料
-> 可实践任务
-> 后续提醒
```

这个功能能让 Link Storm 和普通新闻 App 拉开差距。

### 2.2 灵感捕捉

阅读时快速记录想法：

```text
手机录音
平板手写
二合一/PC 文档笔记
```

第一版只保存原始记录，后续再做语音转写、手写识别、行动项提取。

### 2.3 情报复盘

每周给用户一份复盘：

```text
你本周关注了什么
哪些信号反复出现
你收藏了哪些机会
你错过了哪些活动
下周建议关注什么
```

这个功能比单纯日报更有留存价值。

### 2.4 主题作战室

用户可以为某个主题建立长期追踪页，例如：

```text
AI Agent 出海
人形机器人供应链
深圳低空经济
跨境电商 AI 工具
```

页面包含情报、活动、公司、笔记、行动项。

### 2.5 活动后回流

用户参加或错过活动后，系统继续推荐：

```text
活动资料
主办方后续活动
相关情报
下一场类似活动
个人复盘笔记
```

这样活动不是一次性跳转，而是产品闭环的一部分。

## 3. 信息整合是否需要大模型

长期看需要，但第一版不应该强依赖大模型。

大模型擅长：

1. 长文本摘要。
2. 多来源事件整合。
3. 提炼“为什么重要”。
4. 生成行动建议。
5. 语音/手写/笔记加工。

但大模型的问题是：

1. 成本不可忽略。
2. 质量需要校验。
3. 可能产生幻觉。
4. 批量处理时延迟和费用会增加。
5. 早期数据量小，不值得把核心链路绑死在模型上。

所以 MVP 推荐：

```text
规则和结构化数据为主
大模型作为可选增强
```

## 4. 零成本或低成本实现方式

### 4.1 内容获取

零成本优先级：

1. RSS。
2. 官方网页白名单。
3. 主办方官网活动页。
4. 用户/运营手动录入。
5. 免费开放 API。

不建议第一版依赖付费新闻 API。

### 4.2 内容整合

不用大模型也能先做基础整合：

```text
标题相似度
URL 规范化
来源可信度
主题标签
城市标签
公司/机构关键词
发布时间
事件类型
```

基础模板摘要：

```text
一句话结论 = 事件类型 + 主体 + 影响方向
为什么重要 = 根据主题和事件类型匹配固定解释模板
下一步建议 = 根据用户角色和相关活动生成
```

示例：

```text
事件类型：机器人企业融资
模板解释：融资意味着该方向仍有资本关注，短期可关注供应链、招聘和活动机会。
下一步建议：查看本周本地机器人相关论坛或开放日。
```

### 4.3 推荐

第一版用混合规则推荐：

```text
内容质量分
+ 用户主题匹配
+ 城市匹配
+ 新鲜度
+ 活动关联
+ 多样性
- 已读惩罚
- 不感兴趣惩罚
```

这套推荐不需要模型，也不需要大量训练数据。

### 4.4 语义相似

零成本方案：

1. 关键词标签匹配。
2. 中文分词可先用简单词表。
3. 标题 n-gram/Jaccard 相似度。
4. 事件字段相同则聚合。

低成本增强：

1. 本地 embedding 模型。
2. Ollama 本地模型。
3. 用户自带 API key。
4. 批处理低频调用云端模型。

### 4.5 摘要生成

第一版用模板：

```text
如果是融资：关注资本、招聘、供应链、竞品。
如果是政策：关注城市、补贴、申报时间、适用企业。
如果是产品发布：关注能力变化、替代关系、开发者生态。
如果是活动：关注主办方、议程、嘉宾、报名截止。
```

第二版再接 LLM：

```text
离线批量摘要
只处理高分候选
只处理人工审核后的内容
缓存结果
失败自动退回模板摘要
```

### 4.6 大模型成本控制

如果后续启用大模型，建议：

1. 只处理排名前 20% 的候选内容。
2. 同一 URL 只处理一次，结果缓存。
3. 同一事件多来源合并后再处理，不逐篇处理。
4. 使用小模型做分类，大模型只做最终摘要。
5. 使用离线批处理，不实时调用。
6. 用户请求“深度分析”时再调用。
7. 企业版或会员功能再开启高成本能力。

## 5. MVP 版本功能边界

第一版必须做：

1. 用户兴趣和城市选择。
2. 情报种子数据。
3. 活动种子数据。
4. 规则评分和推荐。
5. 情报与活动关联。
6. 推荐解释。
7. 基础反馈接口。

第一版暂不做：

1. 复杂爬虫。
2. 大模型摘要。
3. 自动语音转写。
4. 深度个性化模型。
5. 社区和评论。

## 6. 当前项目骨架建议

先建立：

```text
apps/api：后端 API 原型
docs：产品和技术文档
data：种子数据
```

API 第一版：

```text
GET /health
GET /api/feed
GET /api/activities
GET /api/profile/:id
POST /api/feedback
```

这样可以先让推荐逻辑真实跑起来，再接鸿蒙端。
