# Link Storm 本地灵感捕捉需求文档 v0.1

日期：2026-06-10  
当前优先级：纯本地想法留存与管理  
暂缓范围：新闻/活动推荐、开放 AI 读写接口、云端服务器

## 1. 产品定位

Link Storm 第一阶段调整为一个纯本地的多端灵感捕捉与想法管理应用。

核心目标：

```text
在任何设备上快速记录想法
-> 自动保存到本地想法库
-> 支持搜索、整理、标签、归档
-> 支持导出
-> 后续再扩展跨设备同步和 AI 加工
```

一句话：

Link Storm 是一个本地优先的想法捕捉工具，手机用语音，平板用手写，PC/二合一用文档，把碎片想法沉淀成可管理的本地知识资产。

## 2. 设计原则

1. 本地优先：默认不依赖服务器。
2. 快速记录：打开即记，少弹窗，少配置。
3. 多端一致：同一个想法库，同一套数据结构，不为不同设备做三套系统。
4. 输入适配：根据设备形态选择最自然的输入方式。
5. 可带走：支持导出 Markdown、JSON、音频、图片等格式。
6. 隐私可控：用户的录音、手写、文档默认只在本地。

## 3. 目标设备与默认交互

### 3.1 手机

默认输入：语音。

典型场景：

1. 通勤时突然想到一个点。
2. 看内容时想快速说一句。
3. 活动现场想记录一个问题。
4. 不方便打字时快速留存。

核心交互：

```text
打开 App
-> 首页显示大号录音按钮
-> 点击或长按开始录音
-> 松手/点击停止
-> 自动保存
-> 可补充标题和标签
```

### 3.2 平板

默认输入：手写。

典型场景：

1. 看资料时随手写想法。
2. 用手写笔画结构图。
3. 会议时写几个关键词。
4. 阅读时做批注式笔记。

核心交互：

```text
打开 App
-> 首页显示写字板
-> 直接书写
-> 自动保存笔迹
-> 可生成预览图
-> 可补充标题和标签
```

### 3.3 PC/二合一

默认输入：文档。

典型场景：

1. 深入整理想法。
2. 写行动计划。
3. 把语音/手写想法整理成文章。
4. 做项目笔记。

核心交互：

```text
打开 App
-> 首页显示文档编辑器
-> 输入标题和正文
-> 支持清单
-> 自动保存
-> 支持导出 Markdown
```

## 4. 核心功能

### 4.1 快速捕捉

捕捉类型：

```text
audio: 语音
handwriting: 手写
document: 文档
```

用户可以手动切换输入模式。即使在手机上，也允许写文字；即使在 PC 上，也允许导入音频。

### 4.2 本地想法库

所有捕捉内容进入统一想法库。

想法列表支持：

1. 时间排序。
2. 类型筛选。
3. 标签筛选。
4. 收藏。
5. 归档。
6. 搜索。
7. 最近编辑。

### 4.3 想法详情

不同类型详情页：

1. 语音：音频播放器、标题、标签、备注、转写状态。
2. 手写：笔迹预览、继续编辑、标题、标签、备注。
3. 文档：标题、正文、清单、标签、引用。

### 4.4 标签与文件夹

第一版建议同时支持：

1. 标签：用于多维分类。
2. 文件夹：用于项目或主题归档。

示例：

```text
标签：AI、产品、创业、待执行、会议
文件夹：Link Storm、个人想法、活动记录、项目备忘
```

### 4.5 搜索

第一版搜索范围：

1. 标题。
2. 正文。
3. 标签。
4. 备注。

语音和手写如果没有转文字，第一版只能搜标题、标签和备注。

第二版再增加：

1. 语音转写全文搜索。
2. 手写识别全文搜索。
3. 本地语义搜索。

### 4.6 导出

导出是第一版必须做的能力。

支持格式：

```text
单条想法导出：Markdown / JSON
语音导出：音频文件 + JSON 元数据
手写导出：PNG 预览图 + 笔迹 JSON
文档导出：Markdown / TXT / JSON
批量导出：ZIP
```

导出用途：

1. 备份。
2. 迁移。
3. 给 AI 工具处理。
4. 发给其他应用。
5. 跨设备手动同步。

### 4.7 导入

为了让导出真正有用，需要支持导入。

支持：

```text
导入 JSON
导入 ZIP 备份包
导入 Markdown
导入音频文件
导入图片/手写预览
```

第一版至少支持导入自己的 JSON/ZIP 备份。

## 5. 暂不做的功能

第一版不做：

1. 服务器。
2. 账号系统。
3. 云同步。
4. 社区。
5. 新闻和活动推荐。
6. 开放给 AI 的直接读写接口。
7. 多人协作。
8. 复杂富文本编辑器。

第一版可以预留：

1. 语音转文字状态字段。
2. 手写识别状态字段。
3. AI 摘要字段。
4. 同步状态字段。
5. 导出给 AI 的标准 JSON 格式。

## 7. 本地存储方案

建议：

```text
关系型数据库：存 ideas、tags、folders、metadata
应用文件目录：存 audio、preview image、stroke json、attachments
```

文件组织：

```text
app_data/
  db/
  assets/
    audio/
    handwriting/
    previews/
    exports/
```

不要把大音频直接塞进数据库，数据库只存路径和元数据。

## 8. 跨设备同步可行性

用户希望在纯本地应用中实现：

1. 设备靠近时同步。
2. 局域网下同步。
3. 不设服务器。

结论：可以做，但建议分阶段。

### 8.1 方案 A：手动导出/导入

难度：低。  
可靠性：高。  
是否需要服务器：不需要。  
第一版建议必须做。

流程：

```text
设备 A 导出 ZIP
-> 通过系统分享、U 盘、文件传输发到设备 B
-> 设备 B 导入
-> 合并想法库
```

优点：

1. 最稳定。
2. 最容易实现。
3. 没有网络和权限复杂度。
4. 也能作为备份机制。

缺点：

1. 不自动。
2. 用户操作较重。

### 8.2 方案 B：鸿蒙同应用跨设备同步

难度：中到高。  
可靠性：取决于系统能力、账号、设备组网和权限。  
是否需要服务器：不需要自建服务器。

鸿蒙有分布式数据和跨设备能力，适合“同一应用在多设备之间同步小规模结构化数据”。华为文档中分布式数据对象用于多设备间对象数据协同，关系型数据库也有跨设备同步能力。

适合同步：

1. 标题。
2. 标签。
3. 文本。
4. 文件夹。
5. 小型元数据。

不建议直接同步：

1. 大音频文件。
2. 大量图片。
3. 很大的手写轨迹文件。

大文件建议走文件传输或分批同步。

产品形态：

```text
附近设备发现
-> 用户确认配对
-> 选择同步范围
-> 同步元数据
-> 按需传输资源文件
```

需要注意：

1. 需要用户授权。
2. 可能要求设备登录同一华为账号或处于可信组网。
3. 需要处理冲突。
4. 需要处理断连。
5. 需要处理大文件失败重试。

### 8.3 方案 C：局域网点对点同步

难度：高。  
可靠性：中。  
是否需要服务器：不需要公网服务器，但需要设备在同一局域网。

实现方式：

```text
设备 A 开启本地同步服务
设备 B 扫描二维码或输入同步码
两端建立局域网连接
交换设备 ID
比较数据版本
传输差异数据
传输资源文件
合并并解决冲突
```

优点：

1. 不依赖云。
2. 可跨不同网络服务商。
3. 理论上更可控。

缺点：

1. 要自己实现发现、配对、加密、传输、断点续传。
2. 移动系统后台限制可能影响稳定性。
3. 安全设计不能偷懒。
4. 开发成本明显高于手动导入导出。

### 8.4 方案 D：靠近即同步

难度：高。  
建议：不作为第一版目标。

“靠近即同步”听起来简单，但真实需要：

1. 设备发现。
2. 身份确认。
3. 用户授权。
4. 数据加密。
5. 冲突合并。
6. 大文件传输。
7. 后台任务管理。

如果基于鸿蒙分布式能力，可能能做得更顺；如果完全自建，会比较复杂。

## 9. 同步冲突策略

即使是纯本地，也必须设计冲突。

每条 idea 增加：

```text
id: 全局唯一 UUID
device_id
created_at
updated_at
version
deleted_at
```

规则：

1. 新增：直接合并。
2. 删除：软删除，保留墓碑记录。
3. 不同字段修改：合并。
4. 同一字段冲突：保留两个版本，让用户选择。
5. 附件冲突：按文件 hash 去重。

第一版手动导入时可以简单处理：

```text
如果 id 不存在：导入
如果 id 存在且导入版本更新：覆盖
如果双方都更新：生成副本
```

## 10. AI 相关策略

当前不做开放 AI 读写接口。

保留：

1. 导出 Markdown。
2. 导出 JSON。
3. 导出 ZIP。
4. 用户手动分享给 AI 工具。

预留字段：

```text
transcription_text
ocr_text
ai_summary
ai_action_items
ai_processed_at
```

后续再考虑：

1. App 内调用系统 AI。
2. 用户自带 API key。
3. 本地模型。
4. AI 插件接口。

## 12. 开发复杂度评估

### 基础本地版

复杂度：中。  
周期：2 到 4 周可做出可用原型。

包括：

1. 三端自适应入口。
2. 录音。
3. 手写板。
4. 文档编辑。
5. 本地库。
6. 基础搜索。
7. 导出/导入。

### 做好想法管理

复杂度：中高。  
周期：4 到 8 周。

难点：

1. 搜索体验。
2. 标签和文件夹体验。
3. 手写笔迹编辑。
4. 音频和笔迹资源管理。
5. 自动保存和恢复。
6. 删除、归档、备份。

### 跨设备同步

复杂度：中高到高。  
周期：额外 4 到 8 周，取决于选择方案。

建议顺序：

```text
导出/导入
-> 鸿蒙同应用跨设备同步
-> 局域网点对点同步
-> 靠近即同步
```

## 13. 第一版建议路线

### v0.1 本地可用版

目标：单设备好用。

交付：

1. 手机录音。
2. 平板手写。
3. PC 文档。
4. 本地想法库。
5. 标签/收藏/归档。
6. 搜索。
7. 导出 Markdown/JSON/ZIP。
8. 导入备份 ZIP。

### v0.2 管理增强版

目标：想法能长期管理。

交付：

1. 文件夹。
2. 删除恢复。
3. 批量操作。
4. 时间线视图。
5. 行动项。
6. 统计和复盘。

### v0.3 跨设备试验版

目标：不设服务器的多设备迁移/同步。

交付：

1. 同应用跨设备同步可行性验证。
2. 同步冲突策略。
3. 小数据同步。
4. 大文件按需传输。
5. 同步日志。

## 14. 结论

纯本地版可以做，而且适合作为 Link Storm 的第一阶段。

推荐当前决策：

1. 第一版不做服务器。
2. 第一版不做开放 AI 读写接口。
3. 第一版必须做好导出/导入。
4. 跨设备同步先预留数据结构，后续优先验证鸿蒙同应用跨设备同步。
5. 靠近即同步和局域网点对点同步不要作为第一版目标。

这样可以先把核心体验做扎实：用户能在手机、平板、PC 上快速把想法留下来，并且这些想法不会被锁死在应用里。
